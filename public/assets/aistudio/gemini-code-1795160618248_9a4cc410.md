# System- & Architektur-Konzept: SidelineOS

**SidelineOS** ist eine quelloffene, modulare und selbstgehostete Multi-Tenant-Plattform von Coaches für Coaches. Sie dient der Taktikauswertung, Teamorganisation und Kollaboration im American Football und anderen Sportarten. Sie stellt eine schlanke, datenschutzfreundliche und kostenfreie Alternative zu kommerziellen Systemen wie Hudl oder Qwikcut dar.

---

## 1. Executive Summary & Zielsetzung

### Core Principles
* **Modul-Architektur:** Ein schlanker Core stellt Auth, Teams, Rechteverwaltung und die UI-Shell bereit. Fachfunktionen (wie die Videoanalyse) sind steckbare Module.
* **Stateless Server & S3 Storage:** Keine Medienverarbeitung oder -speicherung im Anwendungskontainer. Volle Anbindung an S3-kompatible Object Storages (MinIO, Hetzner Object Storage, Ceph, AWS S3).
* **High Efficiency & Raspberry Pi Support:** Durch Browser-seitiges Transcoding (WebAssembly) läuft das Backend ressourcenschonend auch auf minimaler Hardware (z. B. Raspberry Pi im Vereinsheim).
* **Multi-Deployment:** Vorgefertigte Docker-Container, Proxmox LXC Helper-Skripte und Standalone-ISOs für Homelabs und Vereinsheime.
* **Direct Database Single Source of Truth:** Alle Metadaten, Kategorien, Datumszuordnungen und Tag-Schemas liegen ausschließlich in der relationalen Hauptdatenbank (PostgreSQL). Keine trägen Manifest-Dateien auf S3.
* **Separated Asset Management:** Anonymisierte Speicherung im S3-Bucket mit Reference-Counting für ultraschnelles, speichersparendes Team-zu-Team Sharing (Zero-Copy bei derselben Instanz).
* **Hudl-Kompatibilität:** Nativer Import/Export von Breakdown-Daten (CSV/JSON).

## 3. Benutzer- & Rollenkonzept (Multi-Tenancy & RBAC)

Die Instanz unterstützt eine strikte Mandantentrennung (Multi-Tenancy). Benutzer können systemweit und teambezogen mehrere Rollen gleichzeitig innehaben.

```text
+-----------------------------------------------------------------------+
|                         Instance Administrator                        |
|   (System-Konfiguration, S3-Setup, Worker-Pools -- KEIN Datenzugriff) |
+-----------------------------------------------------------------------+
                                   |
         +-------------------------+-------------------------+
         |                                                   |
+---------------------------------+                 +---------------------------------+
|             Team A              |                 |             Team B              |
| +-----------------------------+ |                 | +-----------------------------+ |
| | Team Admin (Head Coach)     | |                 | | Team Admin (Head Coach)     | |
| +-----------------------------+ |                 | +-----------------------------+ |
| | Coordinators / Offense / Def| |                 | | Coordinators / Offense / Def| |
| +-----------------------------+ |                 | +-----------------------------+ |
| | Position Coaches            | |                 | | Position Coaches            | |
| +-----------------------------+ |                 | +-----------------------------+ |
| | Players                     | |                 | | Players                     | |
| +-----------------------------+ |                 | +-----------------------------+ |
+---------------------------------+                 +---------------------------------+
```

### Rollen-Matrix im Detail
1. **Instance Admin (Sysadmin):** Verwaltet Server-Ressourcen, S3-Buckets, Transcoding-Worker, globale Module und Team-Instanzen. Hat aus Datenschutzgründen **keine Einsicht** in die Videos, Breakdowns, Notizen oder Kommentare der Teams.
2. **Team Admin (Head Coach / Orga):** Verwaltet Teammitglieder, Modul-Freigaben, Team-Farben, Breakdown-Schema-Einstellungen und App2App-Sharing-Token.
3. **Coordinators & Position Coaches:** Erstellen Breakdowns, schneiden Tapes, zeichnen Overlays, verfassen Notizen und nutzen den Session-Publishing-Workflow.
4. **Players:** Lesezugriff auf freigegebene Tapes, Smart-Playlists und Unit-Cutups. Erstellung eigener Notizen (falls vom Team Admin aktiviert).

## 4. Storage-Architektur & App2App Sharing

### 4.1 S3 Storage Grid Layout (1 Bucket per Instance)
Es wird **ein S3-Bucket pro App-Instanz** genutzt. Die physikalische Ablage ist auf S3-Ebene flach strukturiert. Zuordnungen zu Kategorien, Event-Datum und Teams erfolgen rein in der Datenbank.

```text
s3://<instance-bucket>/assets/reels/{reel_uuid}/
├── raw_source.mp4         <-- (Optional, Sysadmin-Option: ON/OFF)
└── clips/
    ├── play_001.mp4
    ├── play_002.mp4
    └── ...
```

### 4.2 Metadata-Driven Access Control & Reference Counting

```sql
-- Metadaten & Kategorisierung in der Anwendungs-Datenbank
TABLE media_reels (
    id UUID PRIMARY KEY,
    title VARCHAR NOT NULL,
    category ENUM('GAME', 'PRACTICE', 'SCOUTING', 'SELF_SCOUT', 'CUSTOM') NOT NULL,
    event_date DATE NOT NULL,
    s3_path VARCHAR NOT NULL,
    clip_count INT NOT NULL,
    created_at TIMESTAMP
);

-- Access-Junction Table für Teams (Multi-Tenancy & Zero-Copy Sharing)
TABLE team_reel_access (
    reel_id UUID REFERENCES media_reels(id),
    team_id UUID REFERENCES teams(id),
    shared_at TIMESTAMP,
    PRIMARY KEY (reel_id, team_id)
);
```

#### Same-Instance Exchange (Zero-Copy):
Teilt *Team A* ein Reel mit *Team B* auf derselben Instanz, wird lediglich ein neuer Eintrag in `team_reel_access` geschrieben.
* **Garbage-Collector-Löschlogik:** Löscht Team A das Spiel, wird nur deren Eintrag in `team_reel_access` entfernt. Ein Datenbank-Trigger prüft `COUNT(team_reel_access)`. Erst wenn die Anzahl `0` erreicht, wird das S3-Verzeichnis `s3://.../reels/{reel_uuid}/` physikalisch aus dem Storage gelöscht.

#### Cross-Instance Exchange:
Über Token-Generierung können Tapes zwischen zwei voneinander unabhängigen SidelineOS-Instanzen ausgetauscht werden. Der Import kann als geschützter Direct-Stream oder als physischer S3-to-S3 Kopierauftrag erfolgen.

## 5. Video-Processing & Transcoding Pipeline

Das System unterstützt drei konfigurierbare Transcoding-Modi:

```text
                      +-------------------+
                      |   Raw Video File  |
                      +-------------------+
                                |
             +------------------+------------------+
             |                                     |
             v                                     v
   [ Client-Side Wasm ]                  [ Server / External ]
   - FFmpeg.wasm im Browser              - Local FFmpeg (VAAPI/NVENC)
   - Transcoding auf Client-PC           - ODER External Webhook Worker
   - 0 % Server CPU-Last                           |
             |                                     |
             +------------------+------------------+
                                |
                                v
                   [ Direct Upload to S3 ]
```

1. **Client-Side Offloading (Standard für Low-Resource / Pi):** Der Browser des Uploaders verarbeitet Tapes via `FFmpeg.wasm`. Der Server nimmt nur fertig konvertierte MP4-Clips entgegen. **0 % Server-CPU-Last.**
2. **Local Server Worker:** Verarbeitung via lokalem FFmpeg (mit Hardware-Beschleunigung wie `VAAPI`, `NVENC` oder `rpi-h264`).
3. **External Webhook Worker:** Entkoppelte Konvertierung auf externen Nodes im Heimnetz oder in einer Cloud-Worker-Queue.

### Sysadmin-Option für RAW-Dateien
* **`Keep RAW Source Video after Cut: [ON / OFF]`**
  * `OFF`: Nach dem Generieren der Einzelclips wird `raw_source.mp4` gelöscht (spart S3-Speicherplatz).
  * `ON`: Das RAW-Video bleibt für eventuelle spätere Re-Cuts erhalten.

## 6. UI-Architecture: Modul "Videoanalyse"

Das Modul gliedert sich in folgende Hauptansichten und Workflows:

```text
+-----------------------------------------------------------------------------------+
| Top Navigation: [ Dashboard ] [ Video Editor ] [ Film Room ] [ Playlists ] [ Settings ] |
+-----------------------------------------------------------------------------------+
```

### 6.1 Dashboard & Video-Manager
* **Spiele- & Trainingsbibliothek:** Sortiert nach Event-Datum und kategorisiert nach `GAME`, `PRACTICE`, `SCOUTING`, `SELF_SCOUT`, `CUSTOM`.
* **Bulk-Uploader:** Upload-Zone mit Fortschrittsanzeige für Wasm-Transcoding.

### 6.2 Der 2-Stufen Breakdown-Workflow

#### Stufe 1: Fast-Cut Editor (Raw-Video -> Einzelclips)
Wird ein ungeschnittenes Tape hochgeladen, öffnet sich die Schnitt-Oberfläche:
* **Auto-Out Mode (Schnellmodus):** 
  * Der In-Point für Clip 1 startet automatisch bei `00:00`.
  * Ein Druck auf **`O` (Out)** beendet Clip 1, speichert ihn und **setzt den In-Point für Clip 2 automatisch exakt an diese Stelle**.
* **Explicit Mode:** `I` setzt bei Bedarf In-Points manuell (um Totzeiten oder Pausen zu überspringen).
* **Keyboard-Shortcuts:** `J` / `K` / `L` für Schnelllauf und Frame-by-Frame-Scrubbing, `Leertaste` für Play/Pause.
* Nach Abschluss zerschneidet der WebAssembly-Client (oder Server-Worker) das Video in Einzelclips und lädt sie direkt in den S3-Ordner `clips/`.

#### Stufe 2: Breakdown & Tagging Matrix
Die Hauptansicht zur Auswertung geschnittener Clips:
* **Oben:** Frame-accurate Video-Player mit HTML5 Preloading (für unterbrechungsfreien Wechsel zwischen den Einzelclips).
* **Unten:** Hudl-konforme Breakdown-Tabelle.
* **Keyboard Shortcuts:** Taggen von Feldern (Down, Distance, Hash, Play Type, Result, Formation) rein über die Tastatur.

```text
+-----------------------------------------------------------------------------------+
|  +-------------------------------------+  +------------------------------------+  |
|  |                                     |  | Play Info & Quick Tags             |  |
|  |         HTML5 Video Player          |  | Down: [ 3 ]  Dist: [ 4 ]           |  |
|  |      (Frame-Accurate Control)       |  | Type: [ Pass ] Hash: [ Left ]      |  |
|  |                                     |  +------------------------------------+  |
|  +-------------------------------------+  | Canvas Overlay Control             |  |
|                                           | [Pen] [Arrow] [Spotlight] [Colors] |  |
+-----------------------------------------------------------------------------------+
| Breakdown Data Grid (Hudl-Compatible)                                             |
| # | Play | ODK | DN | DIST | HASH | PLAY TYPE | OFF FORM | DEF FRONT | RESULT | ... |
| 1 | P-01 | O   | 1  | 10   | L    | Run       | Trips L  | 4-3       | +6 yds | ... |
| 2 | P-02 | O   | 2  | 4    | L    | Pass      | Trips L  | 4-3       | Incomplete   |
+-----------------------------------------------------------------------------------+
```

### 6.3 Film Room (Coaching, Canvas & Session Publishing)
* **Vektor-Canvas:** Layover auf dem Video-Player zum Einzeichnen von Freihand-Linien, Pfeilen, Textmarkern und Spieler-Spotlights (Abdunklung des Hintergrunds).
* **Team-Farben:** Anpassbare Farbpaletten pro Team (z. B. Offense = Blau, Defense = Rot).
* **Toggle Auto-Stop:** Automatischer Halt des Videos beim Erreichen einer Zeichnung (an/ausschaltbar).
* **Session Publishing (Draft vs. Published):**
  * Notizen und Zeichnungen verbleiben beim Erstellen im Status `DRAFT` (nur für den Ersteller/Coach sichtbar).
  * Nach der Auswertung schaltet ein Klick auf **"Publish Session (X Items)"** alle Notizen in einem Rutsch für das Team frei und löst optional Benachrichtigungen aus.

### 6.4 Smart Playlists & AI Search Engine
* **Dynamic Filter Grid:** Erstellung von Cutups anhand beliebiger Breakdown-Parameter (z. B. *"Alle 3rd Downs in der Redzone"*).
* **AI Search Engine (Optional / RAG Integration):**
  * Einbindung eines lokalen LLM (z. B. via Ollama) oder einer externen API.
  * Natürliche Sprachsuche: *"Zeige mir alle erfolgreichen Pass-Plays gegen Cover 2 aus den letzten 3 Spielen."* -> Die KI übersetzt die Anfrage in ein strukturierte Datenbankschema-Query.
